### 为便于首版开发采用的默认值（可配置，不是额外的已确认交易偏好）

自动模式暂不加仓或补仓，同一周期只产生一次 50% 减仓目标；减仓未能当日执行的数量默认顺延，明确清仓指令覆盖尚未完成的减仓指令。转强不自动取消已登记的待卖意图。这些是引擎的确定性默认值，可在新版本中调整，不在历史结果里悄悄更改。

手动场景的初始模拟资金预填 **10,000 元，可编辑**，不代表用户真实账户或建议投入金额。自动模式每个 ETF 周期暂用独立的同额虚拟本金作比较，不声称模拟了一个真实共享资金组合。手续费/滑点未配置时只报告毛收益。

**删除 V1.1 的 `tail_nextclose_v1` 尾盘固定退出基线。**&#x4E3B;规则改为 `hermes_signal_cycle_v1`；三日历史触达仅保留为辅助观察。1.5 天是信号观察窗口，不是持仓期限。

### 1.4 8 核 16 GB 执行服务器

保留已有 OCTOP QQ 机器人。PostgreSQL、Redis、OpenResty 与业务容器加入实际可互通的 Docker 网络；不把宿主机网关地址或容器名称写死。

生产 PostgreSQL 暂按 4 GB 容器限制配置，以下仅为起点，不是性能保证：

```ini
max_connections = 60
shared_buffers = 1024MB
work_mem = 4MB
maintenance_work_mem = 256MB
synchronous_commit = on
checkpoint_completion_target = 0.9
```

连接池总量必须低于可用连接数。删除 V1 中“为防拥塞全局必须关闭 synchronous_commit”的要求：数据库驱动异步调用、批量写入和提交是否等待 WAL 持久化不是同一个概念。报告、信号、已保存模拟场景、实盘成交及其 Outbox 默认可靠提交；只有已确认可重建的非关键数据，才允许单独评估事务级异步提交。[R2]

生产 Redis 可先使用单实例、2 GB 容器限制，不强制新增 Redis 集群或第二实例：

```ini
save ""
appendonly no
maxmemory 1536mb
maxmemory-policy volatile-lru
```

快照带 TTL，Streams 保留容量上限且不设置整个流的 TTL；关键结果存 PostgreSQL。内存压力或 Redis 重启时，停止新增非必要缓存并从数据库恢复当前状态，不能为了重建缓存重新请求全部供应商。`volatile-lru` 只淘汰带过期时间的键，但不提供事件永久保存保证，也不能替代容量管理。[R3]

生产部署前完成数据库备份与一次恢复演练、密钥保护及基本健康检查即可。数据库精细调优、全量接口探针和复杂监控大屏不作为第一阶段交付要求。

## 第三章：防 AI 跑偏约束与验收

### 3.1 项目根目录的 README.md 与 CLAUDE.md

```markdown
# 个人股票系统开发约束（V1.4开发基线）

本系统服务于 Hermes 板块轮动、境内 A 股行业/主题 ETF 穿透及策略效果验证。
旧系统只是资产来源，不是必须完整恢复的产品需求。

1. 优先完成：报告 -> 板块 -> ETF/个股解释 -> 买入/减仓/清仓节点 -> 交易周期评价。
   同时支持独立手动节点回测，不以14:30或次日收盘强制决定买卖。
   数据平台、接口看板、目录美化不得成为这条链路的长期前置工程。
2. LEFT/RIGHT 仅盘后参考。不得注册盘中任务、订阅实时事件、增加专用实时采集，
   不得把 LR 结果作为 Hermes 必需输入或开关。

   任一轮都可形成节点；脚本只执行已发布节点、T+1与收益计算，
   首期不另加独立突破/破线买卖逻辑，不新增盘中AI常驻循环。
4. 不要求 100% 数据覆盖，不把 85% 当放行门槛。
   覆盖不足、延迟、IOPV 缺失、链节点缺失不得中止全轮报告。
5. 不设全局秒级时效封锁。允许同日延迟数据和已有低频映射继续使用，
   必须保留源时间；不得把缓存读取时间改成行情观测时间。
```

### 3.2 验收重点：检查业务行为，不只检查 import

保留静态导入边界测试作为辅助，但它不能证明接口没有被间接调用，更不能证明完整率门槛已经消失。首期必须实现下列冻结样本测试，测试不请求真实供应商。

| 测试输入或操作                   | 必须得到的结果                                    |
| :------------------------ | :----------------------------------------- |
| 当前覆盖率 60%，已有板块与报价可用       | 本轮继续输出已覆盖范围的结果，不等待补到 85% 或 100%            |
| 全局覆盖低，但一个关注板块已有充分本地证据     | 仍可分析该板块，不因全市场缺数被一起封锁；不宣称全市场第一              |

| 刷新网页 10 次、WebSocket 重连    | 供应商调用次数不增加                                 |
| 关闭 LR 或运行 LR 盘后任务         | 盘中专用供应商调用为 0；LR 失败不影响 Hermes               |
| 同报告/原提示/ETF 由两个板块命中、任务重试  | 聚合来源、样本计一次；行情更新不新增历史预测样本                   |

| 假日前最后交易日买入                | 最早可卖日期来自交易日历，不简单加一个自然日                     |

门控回归应覆盖配置层、旧函数中的 `fresh`/`complete`/`can_start` 分支、ETF 适配层和前端过滤，不能仅在首页显示“允许部分数据”而后台仍全部拒绝。

### 3.3 完成标准：禁止假成功，失败只影响相应功能

生产分支不以示例数据、固定收益、空数组或catch-all静默吞错冒充真实结果。区分“真实无数据”“部分可用”“请求失败”“等待T+1”“等待价格”“未实现”。同一错误按稳定ID聚合，不每分钟重复刷屏。

调度、报告、信号、场景和成交使用可关联ID；错误摘要至少说明任务、阶段、来源、原因和处理状态。无需保存无限量原始响应或另建日志平台。每条规则实现必须能指出代码入口和行为测试，不以新增环境变量或文档描述当作完成。

已有冻结样例是业务约定。AI不能为了让测试通过擅自删除测试、改预期利润、跳过T+1、恢复100%完整率要求或偷偷调用新来源。确需改规则时说明差异并另建版本；每阶段提交实际变更、通过测试和未实现项。

依赖失败的默认处理局限于受影响功能：QQ故障不重跑AI、单个ETF缺价不阻止其他周期、重计算失败不重启全部服务。持久库不可写时保留未保存状态，不能显示“已记录成功”；历史只读能力在可用范围内继续。

**验收：**&#x4EBA;为制造超时、数据库写失败和未知字段，页面显示对应真实状态而非假0收益；修复错误不修改原有交易规则和测试预期。

第三章的业务测试与附录B/C/D共同构成验收，分阶段实现，不要求为此另建测试平台。阶段报告至少列出：实现入口、运行命令、实际通过用例、未实现项、所需配置和已知限制。没有执行的测试标“未执行”，不能写成已通过。

## 第四章：系统架构与策略运行说明

### 4.1 整体架构：策略优先，数据后台化

保留模块化单体，不改为微服务，不增加独立消息集群，不为每个功能单独建服务。一个仓库、一个后端镜像；API 和后台 worker 使用同一镜像的两个入口，数据采集调度保留在 worker；Hermes 五轮时钟由 OCTOP 原生自动化唯一管理，worker 消费受控任务队列。

```text
外部行情 / 受控 MX 搜索
           |
           v
统一后台采集 -> 可用数据入库 + Outbox（同一事务）
           |                         |
           |                         v
           |                 Redis 当前快照 + 有界事件流
           |                         |
           +------ 共享读取 ----------+----> WebSocket 变化通知
                      |
本地版本化映射文件 ----+
                      v
      Hermes 报告 -> 板块轮动 -> ETF 穿透 / 个股解释
                      |
                      v
              信号、规则版本与证据保存
                  /             \
                 v               v
           QQ / Web 展示      自动周期模拟（50%减仓/T+1/清仓）
                                  |
       手动选择历史节点 ----------+---> 独立手动场景（允许加仓）
                                  |
                                  v
                    收益、自动周期胜率与手动方案比较
                    三日触达为辅助；真实成交为独立账本

LEFT/RIGHT：仅盘后读取已有数据 -> 静态参考；不进入盘中主链。
```

Redis `SharedSnapshot` 保存当前可读状态，Streams 只负责变化通知及有限窗口的事件补齐；PostgreSQL 保存报告、信号、成交和结果。消费者可读取已存数据库结果和本地映射，不再规定“所有历史统计、回测只能读 Redis”。

采集器产生市场数据，策略产生报告及评估，人工记账产生成交记录，三者都有合法写入入口。禁止的是业务读取临时向供应商取数，不是禁止策略保存自己的结果。

Redis 暂不可用或游标已过保留窗口时，读取持久化快照恢复当前页面；重要信号从数据库状态恢复，不能指望短期事件流保存全部历史。首期复用旧广播能力到满足这些要求，不额外追求复杂的全分布式一致性。

### 4.2 1.5 天轮动链、五轮 AI 与盘后任务

所有业务时间使用 `Asia/Shanghai`，日期使用交易日历；不使用服务器当地时区或简单“周一至周五”代替交易日。V1 的五个时点保留，不恢复更早版本的四个节点。

五轮均有同等资格形成买入、减仓、清仓节点；14:30不再享有独占的买入资格。1.5天是观察窗口，持仓不因观察窗口结束而强制退出。

轮动链展示上一交易日 13:05、14:05、14:30 与当日五轮。8 节点是当日尾盘时的完整展示长度，不是每轮启动门槛；09:35 最多已有 4 个时点，缺失历史节点留空，不用后来数据回填成“当时已知”。

| 时间                   | 本轮主要任务                  | 数据与接口处理                                      | 输出                   |
| :------------------- | :---------------------- | :------------------------------------------- | :------------------- |
| 09:35                | 观察隔夜题材与昨日尾盘主线的延续/兑现     | 使用已有共享快照与上一交易日后 3 轮；缺竞价专属数据就描述开盘后表现，不伪称竞价量比  | 早盘关注方向、延续/转弱依据       |
| 10:35                | 观察早盘主线是否延续，排除短时脉冲       | 已有快照计算与受控 MX 证据补充；不要求全市场齐全                   | 强弱迁移、ETF 初选          |
| 13:05                | 午后延续、切换与新催化             | 可延用午前数据并标时间；无新行情时不宣称已确认午后加强                  | 午后关注方向               |
| 14:05                | 尾盘前分歧、抗跌与回撤观察           | IOPV、资金字段可选，缺失不取消穿透                          | 尾盘预备池                |
| 14:30                | 汇总已存在的轮动链，形成尾盘核心观察名单    | 穿透与证据落库后发布，记录实际发布时间；14:30 只是计划时间             | 尾盘关注 ETF、个股解释与主要风险   |
| 共享报价到达时，或交易时段每分钟轻量检查 | 执行已发布信号的模拟订单、T+1解锁和持仓估值 | 只读共享结果；不是额外生成买卖信号，也不为回测增加逐只请求                | 节点、参考成交与持仓变化         |

| 15:35                | LEFT/RIGHT 盘后参考         | 只用已有数据；不足则保留旧参考并标日期，允许后续正常盘后数据到达后重算，不为此启动实时源 | Web 折叠参考，不推送 QQ      |

五轮 AI 沿用技能中的调用预算并在新环境核对，不为凑全覆盖率无限追加 MX 查询。遇到已知 200 行截断，记录返回规模和覆盖范围；只有仍有预算且能改变结论时才做针对性补查，不循环扫描到“全市场完整”。

一轮未获得足够新证据时，可以输出“延续上一轮观察，未新增确认”，也可以减少候选。不能为了每天固定推荐数量而强行产生买入信号。

报告先保存，再通过 Outbox 触发 QQ 和 Web 通知。任务计划时间、数据观测时间、实际发布时间、QQ 投递时间分开保存。程序重启按§4.7.5恢复已持久状态和待执行意图；缺失AI轮次不得无标记回补，不补造历史发布时间或历史成交。

#### 4.2.1 外部请求预算：允许失败，不允许无限等待

所有行情、MX、LLM、QQ请求都必须声明连接/读取或整体等待期限、总尝试次数、所属逻辑任务与调用预算。普通行情和长时间AI分析分别配置，不照搬同一个超时秒数。超时针对“请求等多久”，不是“数据旧多久”。

同一逻辑请求的SDK重试、适配器重试、任务补跑合并计数，不能每层独立重新获得额度。沿用现有供应商限流/补采规则；有冲突先记录，不额外套一层无限重试。重试使用有上限的等待与随机错峰；明确的凭据或参数错误不立即反复尝试。是否重试仍遵守供应商实际契约。[S1]

共享请求按数据源、参数和采样轮次合并，消费者不各自请求；回退来源也计入预算。一次取数失败只降低相关结果，不中止全部ETF分析。LLM结构修复也计入同一轮预算，不为取得“漂亮报告”无限重问。

QQ发送失败只重试投递，不重新采集、重新分析或重新生成交易节点。超过重试预算保留失败记录，不删除已保存报告。

**验收：**&#x6A21;拟供应商连续超时，实际尝试次数不超上限；模拟QQ不可达，报告仍可在Web读取且不新增AI调用。

#### 4.3.1 任务隔离与有界资源

一个worker入口不等于所有任务必须在同一条阻塞执行链运行。调度线程/事件循环只负责调度和短处理；同步网络调用与CPU密集回放不能直接阻塞它。按实际运行方式使用受控异步I/O、线程执行器或固定大小的子进程执行器，不按每个请求无限创建线程/进程。[S2]

首版建议同时执行的重型手动回测为1个，其余进入有长度上限的队列；这是可调默认值，不是交易规则。为定时报告、状态持久化与轻量报价处理保留执行能力，不能只设置一个“优先级数字”却让已运行的大任务独占所有资源。回测取消/超时要能实际释放执行资源与临时文件。

同一场景修订的重复计算请求合并；新修订可以替换尚未开始的旧计算，已保存的研究结果不能被覆盖。拒绝或取消要有明确状态，不能返回假成功。

队列、内存缓存、历史批量读取、每个WebSocket连接的待发送缓冲均有边界。展示类最新快照可合并为最新版本；信号、成交和待执行卖出状态不能当成普通行情帧静默丢弃。慢客户端可断开后恢复，不无限积压内存。

**验收：**&#x8FD0;行大回测同时触发定时报告，API仍可读取，定时任务能开始；快速连续提交同一场景不产生无限队列。

这仍是同一项目、同一worker业务执行入口；Hermes的五轮触发时间在OCTOP自动化统一定义。执行器只是受控执行资源，不新增另一套调度或独立微服务。重回测占用资源上限、队列长度和取消清理策略要在实现中给出可见配置与测试，不能留下无界默认值。

### 4.4 数据保留与最低运维要求

| 数据                             | 首期保留方式                                          | 不得误解的地方                                 |
| :----------------------------- | :---------------------------------------------- | :-------------------------------------- |
| Redis 当前快照                     | 可先设 14 个自然日 TTL，覆盖周末和一般长假；允许提前淘汰并从数据库恢复         | TTL 是缓存回收时间，不是行情可用期；24 小时 TTL 不应导致周末无页面 |
| Redis Streams                  | 限制条数/容量并设置消费保留窗口                                | 超出窗口重新读取持久化结果，不声称可以无限回放                 |
| 已完成的 Outbox 投递                 | 可保留 24 小时，从 `processed_at` 计；未完成或失败待重试的不能按该规则删除 | 每个通知目标独立记录，不能 Redis 成功就视作 QQ 也成功        |
| 通用盘中临时切片                       | 可先保留最近 3 个交易日，批量清理；沿用 Tushare 特定数据集的原有保留规则      | 用于评估的必要信号时点与证据在独立记录中保存，不能一起删掉           |
| 报告、节点、规则版本、自动周期、手动场景、三日统计及真实成交 | 长期保留并备份                                         | 自动/手动/实盘独立，不互相覆盖                        |
| 被节点和场景引用的价格、成交证据与估值            | 与对应结果一并保留                                       | 原始3日临时切片清理不能破坏已保存回测；无历史价格的其他节点显示不可计算    |
| 版本化映射与必要历史权重                   | 保留被报告引用的版本，未引用旧文件可清理                            | 不能用今天映射覆盖昨日评估依据                         |
| 接口错误及简要运行日志                    | 7 天起步，滚动清理                                      | 以已有请求记录统计为主，不为监控额外高频调用供应商               |

清理不与大批量盘后计算抢资源，普通清理采用小批次或已有分区方案。不要求每次删除后执行重型维护任务，不将数据库容量优化作为策略上线障碍。

#### 4.4.1 临时文件统一管理：开发硬约束

**目的：目录集中、及时回收、增长受控。只建立一个轻量管理模块，不把它扩展成新的运维项目。**&#x4EE5;下时长和容量是首版建议默认值，不是用户已经给定的硬件容量判断；实际配置可调整，路径隔离和清理责任不能省略。

**A. 一个可配置根目录，按服务和任务分子目录。**

生产宿主机默认：`/opt/1panel/apps/local/stock-system/runtime/tmp/`。Compose通过`TMP_ROOT_HOST`指定，程序只使用容器内的`APP_TMP_ROOT=/app/tmp`，不写死宿主机绝对路径。开发机使用独立运行目录，避免临时文件进入源码仓库。

```text
stock-system/
├── data/                         # 持久数据，不属于通用临时清理范围
│   ├── mappings/                 # 版本化映射、被报告引用的历史版本
│   ├── evidence/                 # 需文件化的报告/回测证据；也可存PostgreSQL
│   └── ...                       # 经登记的其他持久业务数据
└── runtime/
    └── tmp/                      # 应用唯一临时根；可单独挂受限文件系统
        ├── api/
        │   ├── jobs/<task_uuid>/  # 临时下载、转换、解压等任务工作区
        │   ├── exports/          # 等待下载的临时导出文件
        │   ├── cache/            # 可重建SDK缓存
        │   └── system/           # 库默认临时路径与进程临时文件
        ├── worker/               # 与api相同结构；另可有小体积debug目录
        └── web/                  # 本项目Nginx请求缓冲、运行期临时文件
```

原始响应暂存、解压中间文件、计算中间CSV/JSON、临时图片、下载导出文件和可重建SDK缓存，均适用此约束。`round_pack`中已被报告引用的证据、正式策略报告、模拟订单与成交记录、手动场景、历史价格证据不是临时垃圾，仍按§4.4长期保存。

每个任务使用服务名＋随机任务ID的独立目录，不能直接把用户输入或证券名称拼成任意路径。对导入/解压同样校验路径，拒绝`..`逃逸、绝对成员路径及指向根目录外的链接。临时目录不存密钥、永久Hermes会话状态或唯一数据副本。

**B. 创建、读取和清理都经过统一入口。**

在`shared_kernel/temp_manager.py`提供任务上下文、导出引用、预算检查和回收接口。自写代码必须显式传递任务目录，不能直接调用默认位置不明的`mkdtemp`后不清理。Python高层临时目录上下文可在正常退出及异常展开时回收，但不能覆盖进程被强制终止等情况，因此还需要残留回收。[R7]

SDK/子进程优先设置任务级`cwd`、`TMPDIR`、`TEMP`、`TMP`及它实际支持的缓存目录；继承进程环境前先核对。容器级默认目录是兜底，不能假设所有库都会遵守环境变量。默认环境必须在导入库之前设置，不在多个并发任务中反复修改全局`os.environ`；子进程使用独立`env`。

生产API和worker启用只读根文件系统，仅开放受管临时挂载和明确的持久数据挂载；Python禁止运行时写`.pyc`。硬编码`/tmp`和`/var/tmp`的库通过绑定到受管`system/`目录兜底。只读根文件系统并不能辨别已授权`data/`中的文件性质，因此持久目录仍须按模块登记写入口并做测试，不能声称一条Docker设置解决所有越界。[R8]

导出文件直到HTTP响应完全关闭、下载引用释放后才允许清理，不能在响应尚未读完时退出临时上下文。正式报告或证据从临时区转存时，先确认持久写入成功、再删除临时副本；跨文件系统不假定`rename`必然成功，采用持久目标内的小型受管提交暂存、校验、同文件系统原子替换并立即清理。此提交暂存是唯一受登记的短时例外，不得成为data中的常驻垃圾目录。

**C. 清理不是每天一次删目录，而是分生命周期。**

| 类别                   | 首版默认             | 安全条件                                     |
| :------------------- | :--------------- | :--------------------------------------- |
| 任务中间文件               | 任务成功/失败后立即清理     | 先关闭句柄与子进程；先持久保存需要保留的结果                   |
| 异常退出留下的任务目录          | 启动检查；运行中每15分钟检查  | 确认任务锁已释放、相关进程不再写入且完成持久结果核对后回收；无法确认则跳过并提示 |
| 临时导出文件               | 最长24小时，可提前删      | 到期且没有活动下载引用；已归档的正式导出另存持久区                |
| 调试片段/失败诊断            | 最长24小时且体积受限      | 默认只保留小摘要，不无限复制原始响应/全部行情                  |
| 可重建缓存                | 容量受限，默认闲置24小时可回收 | 按组件支持的关闭/失效方式；不删正在使用的缓存数据库               |
| SDK/system、Nginx临时内容 | 由所属任务/进程生命周期释放   | 进程仍活动时不按文件年龄盲删；对旧进程代际的遗留在确认停止后回收         |

回收由现有worker的轻量维护任务完成，不调用供应商或AI。任务和下载持有锁/租约，删除前再检查并取得回收权，避免“检查时未用、删除时正在用”的竞争；仅看文件修改时间或一个可能复用的PID不够。卡死任务按任务执行超时先停止、释放引用，再清理；不能把“禁止误删活跃任务”变成无限占盘许可。这不是行情时效门槛。

清理器只处理已登记且位于根目录真实子路径中的资源，不跟随目录链接、不越过额外挂载、不删除临时根本身，不执行宽泛`rm -rf`或盲目`find -delete`。遇到无登记文件先列出占用、确认所属服务，不直接猜测可删。清理必须幂等；失败记录路径、数量、原因，下轮有限重试。保留句柄的已删除文件、权限失败等异常也要在空间仍未释放时提示，不能只看到文件名消失就报告已恢复容量。[R10]

临时目录在容器启动前按实际UID/GID创建，API和worker使用一致且已授权的服务身份；不要以`chmod 777`解决权限。Nginx自有目录由对应服务维护，普通worker不能为了清理而取得整个宿主机root权限；无法安全回收的网关残留在该服务停止后处理。

**D. 容量保护必须有实际动作，不是只在配置里写数字。**

首版建议：根目录应用预算2GiB（跨API、worker、web合计，不是每个各2GiB），单任务临时写入256MiB，根目录文件/目录条目上限20,000。达到预算80%时执行安全回收并告警；达到预算或持久数据所在宿主文件系统剩余不足5GiB时，优先暂停新的大导出、调试快照和非必要文件落盘。数字可按实际负载调整，不限制Hermes必须取得的数据完整率。

创建前预留预算，并发任务合并计数；下载、解压和写入过程中持续校验，不能只在任务开始量一次大小，也不信任压缩包声明大小。超预算任务停止继续写入，关闭句柄并返回具体原因；不能向临时目录之外“换个地方继续写”。使用已有内存/数据库结果的策略和页面尽可能继续，但持久化真正失败时必须显示未保存，不能虚报信号已可靠落库。


**应用预算不等于操作系统硬配额。**普通bind mount只是位置映射，不会因为存在`APP_TMP_BUDGET_BYTES`就自动限制磁盘容量。若要防住失控第三方进程绕过Python管理器，应在部署时为这个目录启用适合实际文件系统的目录配额，或挂独立且有容量上限的文件系统，并做超限写入测试。不能未经确认格式化/分区现有磁盘；未配置硬配额时明确标为“应用预算保护”，不声称绝对不会占满磁盘。[R8]

若采用独立小容量临时文件系统，2GiB预算针对它；5GiB剩余空间保护针对持久数据/数据库所在的宿主文件系统，不能拿5GiB规则检查一个总容量只有2GiB的临时卷。其他磁盘分别看各自剩余空间。不要把全部大临时文件改到内存盘，转而占满4GB开发机内存。

**E. 日志和基础设施不冒充临时文件。**

业务日志输出到stdout/stderr，沿用§7.1每个容器`10m × 3`的Docker日志轮转；禁止额外再写一份无限增长的`app.log`。需要文件日志的SDK必须单独登记位置、大小与保留数量。[R9]

数据库表、PostgreSQL内部临时文件/WAL、Redis持久化、Docker镜像/构建缓存、系统日志和已有OpenResty/OCTOP的数据由各自组件管理，不迁入应用临时目录，也不能用本清理器直接删底层文件。沿用原保留/备份/轮转策略，部署时核对这些实际占用；“应用临时目录已清空”不等于“整个服务器不会满”。本项目stock-web自有的Nginx缓冲路径须显式纳入web命名空间；共享OpenResty的全局目录不能未经确认挪动或批量清理。[R11]

运行状态页只需增加临时占用、文件数、最近清理时间/结果、预算或硬配额状态及空间不足原因，复用现有页面。手动按钮只能调用同一安全清理逻辑，不提供“无条件清空全目录”。

### 4.5 完整率与时效：允许降级，不制造事实

完整率只告诉使用者“本次观察了多少”，不承担全局开关职责。展示口径必须包含分母来源；只拿到局部篮子时，不把篮子内排名写成全市场排名。

| 情况 | 系统怎样继续工作 |
| :--- | :--- |
| 覆盖达到或超过 85% | 正常分析，但仍保留缺失范围，不能宣称全量 |
| 覆盖不足 85% | 继续分析已覆盖数据，提示局部覆盖；不等待补齐、不全局禁用 |
| 新一轮采集失败、旧同日快照尚在 | 使用原时间的旧快照，报告注明未刷新；不能当成新行情形成第二次突破 |
| 同日数据延迟较久 | 可做轮动参考及带时间的观察；需要比较两个时点的规则，在缺后一个时点时仅不确认该条变化 |
| 昨日行情、盘后日线或跨日背景 | 保留历史参考，不包装成今日现价/今日已发生的突破；当前无法计量的交易评估标待数据 |
| IOPV、资金流或可选盘口缺失 | 不阻止 ETF 映射、候选展示及已有价格分析；对应指标显示缺失而不是 0 |
| 最新映射更新失败 | 沿用最近成功的本地版本，显示版本日期；不在页面点击时回源 |
| 只有部分权重 | 输出已知暴露和覆盖说明，或只展示关联；不得将未知成分权重补 0 后冒充完整暴露，也不把已知子集强行归一成全组合 |
| 某标的身份无法识别、价格非数值或非正、明显未来时间 | 只排除该条有问题的事实/价格，不中止整个报告或其他标的 |
| 本轮完全没有可用行情 | 输出已有报告、历史背景及定性观察；可以没有新的价格信号，不伪造候选成交价 |

“超过 90 秒全部失效”“不到 85% 不运行”“IOPV 缺失全池封锁”“必须 8 节点齐全”均不得出现在新系统的通用门控中。提示阈值可配置，但不隐式转成删除数据或屏蔽结果的条件。

宽松运行不等于强制给出确定结论。缺少某项计算真正必要的输入时，少算该项、说明不足，而不是把整个项目卡住。例如，可以判断某板块仍值得观察，但在没有任何可用价格时不计算该 ETF 的参考收益率。

### 4.6 ETF 穿透与交易范围

**境内上市不等于 T+1。**交易所资料区分境内 A 股股票 ETF 与债券、黄金、货币、商品、跨境等产品：前者二级市场买入份额按 T+1 卖出，部分其他类别支持当日回转。排除境外 ETF 本身并不足以推导全部剩余 ETF 都是 T+1。[R1]

本期先按与板块轮动最匹配的范围实施：**境内 A 股行业/主题股票 ETF、二级市场普通买卖、T+1**。境内上市但投资境外市场的跨境 ETF 同样排除；债券、黄金、货币、商品 ETF 暂不加入，不以基金名称或代码前缀单独推断产品范围。基础资料记录品种、投资范围和交易规则。

低频数据使用版本化本地文件：板块成员、ETF 与跟踪指数关系、指数成分权重、产品分类。更新由受控后台任务执行，业务只读文件。报告记录实际使用的映射版本和当时已可取得的权重日期，不要求“每日全新权重”。

保留现有穿透逻辑的核心含义：在完整已知的指数权重基础上，计算某板块成员所占权重，解释哪些 ETF 对该方向更有暴露，以及哪些成分股对 ETF 具有解释作用。不能把“涨幅最高的 ETF”直接等同于“受该催化影响最大的 ETF”，也不能把简单列出权重股称为新增受益逻辑。

资料不完整时，仍可显示已知关系和部分证据，不因为缺少一项规模、IOPV 或流动性历史数据就全局停止。原权重归一化、打分及筛选规则作为基线；需要调整阈值时新建规则版本，通过后续结果比较，不承诺修改后必然提高胜率。

2026-11-17方向优先整改（用户授权）：新轮次采用`etf-direction-first-v2`，AI通过技能从有来源关联的候选事实中显式选择ETF；主板比例、核心集中度、固定涨幅、均线等只作研判参考。程序核验实际产品范围、交易规则、交易单位和有效报价，QQ、工作台及模拟入场共同消费同一份已保存结果。旧版量化策略保留用于历史对照，已有周期数量、T+1、退出规则及历史事实保持冻结。研究资料采集范围与执行准入分离；无完整权重时保留已核验关联、标明未知暴露，不补造数字。完整实现与验收见[ETF方向与执行统一整改](etf-direction-unified.md)。

### 4.7 自动记录：向好买入、首次转弱减仓50%、退潮清仓

自动记录是系统按既定规则进行的本地模拟，**不是自动下单，也不等于用户真实买卖**。规则版本为 `hermes_signal_cycle_v1`。

#### 4.7.1 节点与周期

| 情况 | 自动动作 |
| :--- | :--- |
| 没有该ETF的在途买单或持仓，Hermes明确向好并筛出它 | 记录BUY节点，开启待建仓周期 |
| 已经持有，同一轮或后续轮继续向好 | HOLD；不重复买入、不自动加仓 |
| 首次明确转弱且已有真实模拟持仓 | 记录REDUCE节点，冻结目标卖出数量＝信号时实际持有份额×50% |
| 重复转弱或减仓完成后再次转弱 | 不再次产生50%目标；仍跟踪原待执行订单或保留余仓 |
| 减仓之后再次转强 | 首版继续持有剩余份额，不自动补仓，不重置“已触发首次减仓”标记 |
| 明确完全退潮 | 记录EXIT节点，目标清理本周期剩余份额；未完成的减仓被替代，不重复计算卖出 |
| 直接从向好变成明确退潮 | 可跳过减仓直接清仓 |
| 候选未再次出现、某轮缺失或没有新判断 | 不等于转弱或退潮，维持状态；缺数据不能伪装成卖出信号 |

买入和加仓权限不同：自动模式首版没有ADD，手动模式允许ADD。只有实际模拟持仓归零，周期才算结束；发布清仓信号但等待T+1或价格时仍是待退出周期。未成交的买单若先收到明确转弱/退潮，取消未成交买单，不在后来的价格恢复时倒补旧买入。

每轮除发现新机会，还应评估已有持仓的原关联板块，明确输出维持、转弱、退潮或未知；不能只追踪当轮新推荐。多个板块对应同一ETF时，聚合来源、不重复买入，并在入场时冻结用于退出判断的主关联板块/原始理由。以现有穿透排序产生的主关联为默认；不能根据事后表现切换到另一个板块延长持仓。其他方向的相反判断作为备注，不叠加多套卖出订单。

原始Hermes文本和JSON保存不变，适配层增加规范化状态及证据。具体怎样从报告识别“明确转弱/完全退潮”沿用当前技能语义和已有规则，记录版本；无法明确映射就标观察/未知，不擅自补出新的评分阈值。

**规范化适配和运行期工具权限。**

保留原始报告和既有JSON，在适配层明确已有语义如何映射为“向好、维持、转弱、退潮、未知”。可以使用枚举字段，但不得破坏旧schema。对应板块、ETF标识、证据与原报告引用必须可追溯。

不能只搜索“弱”“风险”“退潮”等单字词决定买卖。例如“尚未出现退潮”不等于退出。字段缺失、逻辑冲突或标的无法匹配时，仅将相关标记置为未知/待确认；报告和其他有效标的仍可发布。默认不凭空产生BUY/REDUCE/EXIT，不把未知当卖出。

AI负责研判；交易引擎负责50%数量、T+1、现金、可卖量和利润。模型给出的数量/收益不能未经引擎计算直接写入账本。

2026-11-17补充：每个OCTOP已发布轮次可以在同一worker中推进有界的成交补价阶段。只为处于交易时段且已具备交易资格的待价格订单调用共享ETF行情入口；发布后30、120、300秒到期，至多3次，重启和手动恢复共用持久请求预算。源报价必须晚于节点，复用相同报价不得重复成交。此阶段不新增AI研判、不重新发送报告，调度归属仍是OCTOP原轮次。

运行期Hermes仅获得研判需要的受控只读工具。不提供任意SQL写入、系统命令、删除文件、修改配置、读取密钥或外部账户交易权限。历史技能中的写工具不能因整体复制目录而默认启用。外部新闻、网页和MX返回的文本视为资料，不是系统命令；提示词之外仍需工具侧权限检查。前端展示外部/AI内容也不能直接执行其HTML或脚本。[S3]

现有持仓摘要和已触发减仓标记来自数据库，不能随着1.5天观察窗口滚动丢掉。重放已有报告直接使用已保存的规范化结果；再次调用模型重判属于新的研究版本。

**验收：**“尚未退潮”不触发清仓；一只ETF输出损坏不阻止其他结果；外部文本要求删除数据库时，Agent无此工具权限。

#### 4.7.2 50%目标只计算一次

首次转弱时先读取**本周期实际模拟持有总份额**，而不是只读取当日可卖份额。随后冻结目标数量，并单独累计已经卖出的数量：

```text
减仓原始目标 = 首次转弱时总持仓 × 50%
本次可模拟卖出 = min(尚未完成的减仓目标, 当前可卖份额)
剩余减仓目标 = 原目标 − 已按该目标卖出的份额
```

50%是份额比例，不是卖出本金的50%，也不是卖出“当前可卖量的50%”。因T+1分两天完成同一减仓目标，只算一次减仓事件；不能次日又对剩余持仓重新乘50%。

按标的交易单位将目标向下取整并同时展示理论比例和实际份额。普通ETF二级市场通常以100份为一手，首版依据标的规则读取交易单位。[R1] 若不足一个有效交易单位，保留目标及原因、不虚构零碎成交；等待清仓或另一个明确新规则处理，不擅自改为卖100%。首次建仓数量也按同一交易单位与可用现金取整。例：持仓1,100份，减仓理论550份，按100份单位实际目标500份，页面必须显示实际约45.45%，不谎称实际成交恰好50%。

#### 4.7.3 T+1与顺延：按每次买入批次处理

范围限定境内A股股票ETF二级市场普通买卖。T日买入份额最早在下一交易日卖出；卖出回笼资金可用于当日后续买入，但新买入的份额重新按T+1锁定。[R1] 不讨论一级市场申赎通道。

每次BUY/ADD成交生成一个批次，记录买入日期、数量和 `sellable_from_date`。卖出默认从已解锁批次中先进先出扣减。FIFO只是本方案的模拟配对选择，不宣称是交易所规定的成本会计方法。

| 场景 | 处理 |
| :--- | :--- |
| 当天买入1,000份，当天首次转弱 | 记录减仓500份意图，当天卖出0，下一可卖交易日再按当时可用价格处理 |
| 旧仓500份，今天加仓500份，目标减仓500份 | 可以卖旧仓500份，当天新买500份仍锁定；主要用于手动模式 |
| 旧仓200份，今天加仓800份，目标减仓500份 | 先卖200份，剩余300份顺延；不把目标缩成100份或扩大成另一个50% |
| 当天先转弱后明确退潮，减仓尚未执行 | 取消未完成的减仓余额，改为清剩余总持仓；不能叠加成卖出150% |
| 前一日已有减仓成交，后续退潮 | 清仓只针对剩余份额，已经减掉的部分不再计算 |
| 周末、节假日、停牌或无可用价格 | 交易日历确定解锁日期；解锁不保证立刻成交，仍等待合法时段的有效参考价格 |

默认待卖指令持续有效，直到完成或被新的明确清仓替代；再次转强不会默默撤单。这个默认规则保存于评估版本，后续需要“转强撤销待卖”时另建对照版本。清仓优先于减仓，同一数量不可同时占用两个未完成卖单。

#### 4.7.4 节点时间与成交时间分别保存

记录 `signal_at`、`requested_at`、`eligible_at`、`filled_at` 和价格来源。原节点先保存，不等待全市场补齐；参考成交只能采用节点产生后、份额已可卖且处于合法交易时段的已有可用价格。补到的是节点之后的历史价格可以用于历史重放，但不能把节点之前的报价当作之后成交。

未取得价格时显示待价格，数据后续正常到达再重放。上一笔报价可以作为观察参考，但不得伪装成延迟卖单的实际成交价。无需新增秒级接口或100%完整门槛。所有成交均为模型参考，不保证现实能够按该报价成交；已知停牌或明显不可交易的节点不得强行成交。

同一时点并存节点时使用稳定排序：先应用已发布的明确退出/撤销状态，再处理合法卖单，最后处理买单；同等级按来源节点ID/手动排序号。保存实际采用的顺序，不能利用同一时刻的资金重复买入。

#### 4.7.5 重启恢复、活动周期唯一与执行规则固定

持仓批次、减仓原目标、已完成量、待执行余额及周期状态必须可由持久账本恢复。数据库事务内完成一次成交及对应份额/现金状态变化；Redis只作缓存，重启不能把“已经减仓”标记清空。

同一自动运行空间内，同一ETF同时最多有一个待建仓、持仓或待退出周期。不能只依赖每个scenario内部唯一键，而每次新报告又创建新scenario绕过去。独立研究版本必须显式放到另一个运行空间，不污染自动基线。

并发写入由短事务、行锁或带版本条件的更新保护。持有订单/场景锁期间不得等待LLM或QQ。任务租约过期后重试，旧任务迟到提交也须被版本/执行权校验挡住，不能依赖“看起来只启动了一个worker”。

每个已开启周期固定其执行规则版本：减仓比例、待卖是否顺延、手续费口径、舍入及取价规则不被新版全局配置悄悄替换。后续AI报告仍保存其实际模型/提示词版本；不能把跨研判版本的周期伪称完全由同一版本产生。新执行规则仅用于新周期，或通过明确的新研究场景对照。

重启先恢复状态，再恢复调度。错过的AI轮次不并发补成一堆“当时已经发布”的报告；可以保留缺轮、恢复当前轮，或单独标记迟到报告/历史研究。已发布待卖意图则必须恢复，不能随着过期调度被丢弃。按固定APScheduler版本配置并发、错过执行和合并策略，不能误以为合并所有任务都安全。[S5]

**验收：**减仓成交后强制终止进程，重启不再卖一次50%；清仓与减仓并发时同一份额只卖一次；新版本发布不改变旧周期剩余目标。

“自动运行空间”区分正式自动基线和明确新建的研究运行；默认正式基线使用单一空间。它不是每份报告或每个周期随意生成的新ID。普通新报告必须继续查找同一空间下该ETF现存周期。没有结束的周期不能因进入下一交易日、跨出1.5天窗口或软件升级而消失。

### 4.8 手动回测：自己组合买入、加仓、减仓、卖出节点

这是**历史组合试算**，不是把真实成交填入记账表，也不是修改Hermes原始推荐。一个手动场景可以仅含一只ETF，也可以含多只ETF；同场景内共享一份初始现金，所有节点统一按时间重放。

#### 4.8.1 用户操作

打开某ETF的轮动/价格时间线，选择已经保存的Hermes节点，或选取本地已有历史报价时点，设置动作：

| 动作 | 用户指定内容 | 计算基准 |
| :--- | :--- | :--- |
| 买入 | 金额、份额或可用现金比例，三选一 | 当时可用现金，不是每次都取初始资金 |
| 加仓 | 金额、份额或可用现金比例，三选一 | 新增买入批次，独立计算T+1 |
| 减仓 | 持仓比例或份额；界面默认50%，允许修改 | 所选节点时该ETF的实际总持仓；目标数量随整场重放计算 |
| 卖出/清仓 | 剩余全部，或明确份额 | “全部卖出”覆盖同ETF尚未完成的旧减仓目标 |

界面“卖出”默认解释为清掉剩余仓位；要卖部分就选择减仓。用户可以跳过自动买点、提前或延后选点，也可从自动周期复制出一份手动场景再调整，原自动记录不变。

初始模拟资金预填10,000元，可修改；这是计算参数，不是用户实际资产。未配置费用时用毛现金流重放并标未计成本。需要固定佣金、最低收费或滑点时由用户设置，不能暗填真实券商费率。

选择节点后，界面立刻预览：节点时间、参考价格及其时间、动作、目标份额、可卖份额、预计参考成交时间、成交后现金与持仓。点击“计算”生成结果；编辑、撤销和复制都生成新的场景修订，不覆盖已保存结果。

#### 4.8.2 手动模式同样遵守T+1和现金约束

不因用户手工点选就允许当日卖出新买份额。遇到T+1限制时，草稿保留原意图，预览中明确标出“原节点不能成交，剩余数量顺延至下一可卖时点”；运行结果同时显示原节点和实际模拟成交节点，不能悄悄换日期仍显示原日成交。

卖出数量不能超过该场景持仓，买入不能超过当时现金；出现冲突时保留草稿，指出具体节点并允许调整，不借钱、不自动充值、不产生负份额。T+1顺延本身不是场景失败；数量/现金不可能的节点则不进入正常收益统计。

默认未完成的减仓目标总量与新减仓目标合并校验，合计不可超过剩余持仓。手动明确清仓则替代未完成减仓。修改早期买入后必须从场景开头重算后续现金、百分比目标、可卖量和收益，不只修改最终利润数字。

没有本地价格时该节点显示待价格，不阻止查看其他场景，也不触发供应商补采。可另设明确标记的“自填假设价格”用于试算，必须与引用真实历史价格的结果分开，并保留原时间和来源；价格手填不能绕过T+1。

#### 4.8.3 两种模拟共用引擎，三个账本独立

自动模式自动产生节点，手动模式由用户选节点；二者共用现金、T+1批次、参考成交和收益计算代码，避免同一组操作算出两套结果。真实成交只存在独立实盘记账，不被模拟更改。

手动回测可以事后挑选好看的节点，这对研究有用，但该结果只代表所选组合，不能并入自动信号胜率。自动与手动比较时展示相同区间、价格和成本口径；不相同的条件必须标出，不能直接排列成算法优劣结论。

### 4.9 利润率、自动胜率与辅助指标

#### A. 自动周期收益

一个周期从实际模拟买入开始，到该ETF所有份额实际模拟卖完结束。两次分批卖出不算两个独立“胜利样本”。买入未成交、等待T+1、待价格、仍有持仓均独立显示。

首版每个自动ETF周期使用独立的同额模拟本金，例如10,000元。可以汇总周期胜率及平均收益，但不能将多个重叠周期视为共用同一笔钱的账户曲线；同一资金组合留待明确分配规则后单独实现。

```text
当前现金 = 初始现金 − Σ买入金额 + Σ卖出金额 − Σ已配置交易费用 + 已确认现金分配
期末权益 = 当前现金 + Σ剩余份额×对应估值价
组合利润 = 期末权益 − 初始现金
组合利润率 = 组合利润 / 初始现金 × 100%
```

自动模式首版无加仓，周期也可以补充显示“利润÷实际买入总成本”的投入成本收益率。它与按初始本金计算的场景收益率分母不同，必须分别命名，不混排。

#### B. 手动场景利润率

手动主指标使用同一份预设初始资金：`(期末权益−初始资金)/初始资金`。资金在减仓后再次用于加仓属于内部循环，不重复计入外部本金。首版不引入中途外部入金/出金；要增加场景资金，修改初始资金并重新计算。

未清仓时分开展示已实现盈亏、未实现盈亏、持仓及估值时间。总利润率包含剩余持仓市值，不能把所有买入金额先减掉却漏掉剩余持仓。没有估值价时仍展示已实现部分，总利润率标暂不可确定，不将未知市值填零。

毛收益不扣未设置的成本；已完整设置费用和滑点才报告净收益，滑点若已经体现在模拟成交价格中不能再扣第二次。每笔利润率不能直接相加，加仓的比例也不能不说明是占现金还是占持仓。

**冻结演算例（假设价格，未计费用）：**初始10,000元；T日买5,000份×1.000；T+1日先加4,000份×1.100，再卖4,500份×1.200；T+2日卖剩余4,500份×1.100。T+1日卖出的4,500份来自旧仓，满足本方案的T+1配对。买入合计9,400元，卖出合计10,350元，期末现金10,950元，利润950元，**场景利润率9.50%**。利润÷累计买入金额约10.11%，是另一个成本口径，不能代替9.50%。

持有期遇到分红、份额变动时，执行价格使用可成交价格，现金分配/份额调整独立登记，不以复权价充当成交价。尚未接入某项事件数据时保留已知价格结果并标“未完整计入分红/份额事件”，不停止其他回测，也不声称已经得到完整总回报。

#### C. 自动胜率与尚未完成周期

```text
自动毛收益胜率 = 已闭合且毛利润>0的周期数 / 已闭合且可计算毛利润的周期数
自动净收益胜率 = 已闭合且净利润>0的周期数 / 已闭合且成本配置完整的周期数
```

持平计入分母但不计盈利；未结束和缺数据不记亏损，也不从页面消失。特别是可能长期未退出的亏损周期，必须同时显示当前浮亏、持有时长和未退出数量，避免只呈现已经盈利结束的周期。首期显示周期数、胜率、平均盈亏、盈亏大小关系与持有时间，不为追求漂亮胜率剔除不利样本。

#### D. 三日历史触达和真实成交

保留V1.1的辅助口径：按报告ID、原提示和ETF生成观察样本，以报告后下一交易日开盘参考价为起点，观察该日起三个交易日是否曾向上触达。它不是本次主入退场规则，也不是可实现利润；参考入场日的高点不能当作当日可卖收益。另算可卖窗口时明确日期。

真实成交按用户实际时间、价格、份额和费用计算；数量尚未补齐时只显示能够确认的部分。手动历史组合与真实手动成交必须分开，不因都带“手动”二字混进同一表或胜率。

#### E. 市场形态与版本比较

延续V1.1：使用当时可得的大盘背景作上涨、震荡、下跌或未知标签；未知不阻塞。门控、提示词、退出规则、费用模型改变均保存新版本，不能事后重写过去信号。“向好—减弱—退潮”的阈值后续可迭代，但不是这次需求中已经给定的公式。

### 4.10 本期开发优先级

先用冻结样本跑通自动买入、一次50%减仓、退潮清仓、T+1批次和利润计算；随后在同一引擎上增加手动选择、复制、编辑和重算。接入五轮真实报告与已有行情后持续积累样本，三日触达与细化运维后排。

不要求新增高频接口，不要求100%覆盖或秒级时效；必要价格缺失只影响对应成交/指标，不能挡住节点保存、报告展示或其他ETF的评价。

本版的`simulation_*`仅用于本地模拟，不接任何券商或外部模拟交易账户。一个手动场景在同一事务/场景锁内更新订单、批次扣减和现金结果；同一份额不能被重复卖出。应用层必须校验订单、周期、成交属于同一场景且ETF一致，费用非负、现金非负、批次已解锁、累计卖出不超过批次买入量。以上跨表与时序规则不靠这份参考DDL自动保证，需测试。

本版为已确认的恢复/唯一性约束补充`auto_scope_key`、`execution_snapshot`、`row_version`和`execution_token`。AUTO周期的运行空间必须由环境/研究运行确定且非空，MANUAL不得占用正式自动空间；应用层在同一短事务中检查场景模式、唯一索引冲突和状态变化。只创建字段不代表已实现幂等或执行权保护。`CLOSED`只能在实际模拟份额归零后写入，不能收到EXIT信号就提前结束周期。

已保存场景修改时创建新场景，`parent_scenario_id`指向来源；节点版本、价格证据和成本配置进入输入清单。待数据的模拟可以按同一规则重放，记录输入修订，不改原始Hermes信号。买入成交本身作为批次，不必为了“架构完整”再加独立交易微服务。

结构设计不以表数越少越好为目标，也不以恢复旧表越多越好为目标。必须能回答：何时发布、用了什么依据、哪个版本、参考入退场怎样确定、哪些样本尚不能评估。

原 V1 把整轮多个 ETF 的效果放在一行的几个汇总字段中。本版改成单标的、单评估规则保存，汇总时再计算，避免把多只 ETF 的最高价、平均值和交易结果混在一起。

基线报告发布后不得用未来新映射覆盖原证据。重放和研究比较另存带版本的研究结果，不伪装成新增实盘报告。结果补数或纠错记录输入版本、原因及更新时间，不能悄悄改原始信号。

已发布报告及规范化结果的模型、提示词、适配器和输入版本保存在外层元数据/记录列；周期执行快照与报告研判版本不是同一个版本号。含多个研判版本的周期如实标记，回放已有规范化节点不再次调用AI。

#### 5.1.1 数值、标识和输入时间契约

适配层统一标的标识、交易所、价格币种、金额、成交量、比例和时间字段。保留代码前导零；禁止以名称作为唯一标识。供应商的“手/份”“元/万元”“3/0.03”等差异按实际文档转换，不能猜测。

账本金额、费用和订单计算使用从字符串等精确输入构建的Decimal，数据库沿用NUMERIC；定义精度、舍入方式与触发舍入的环节。不要先转float再转Decimal。图表显示可格式化，但不能把页面四舍五入后的数值送回作为下一笔计算输入。份额按标的交易单位处理；缺失值不等于0。[S4]

行情至少保留观测时间与接收时间，报告另有发布时间。晚到的旧响应不能因为“刚收到”就覆盖更晚的当前行情。相同观测时点的合法修订须带来源/修订标识并按明确规则处理，不一概忽略，也不偷偷修改已发布报告的证据。

一次研判保存所用输入版本清单，不要求不同数据必须完全同时。保持本版允许延迟数据的规则；这里限制的是时间顺序错误，不是延迟本身。

**验收：**不同单位的等价输入得到一致结果；旧响应晚到时当前快照不倒退；边界金额不会因浮点误差多买一手或产生微小负现金。

上述转换在数据适配和计算引擎中统一完成。只有相关事实无从可靠识别时限制该项，不能把单位与账目校验扩展成全市场完整率封锁。精度、舍入、取价顺序进入执行规则快照，前后端不各维护一套利润公式。

### 5.2 Redis SharedSnapshot 与本地文件

| 键或文件 | 内容 | 说明 |
| :--- | :--- | :--- |
| 现有市场共享快照键 | 已采集行情与原时间 | 优先沿用旧协议，不为改名重写客户端 |

| `snap:hermes:cycle_positions` | 自动周期持仓、可卖量、50%目标、待清仓状态 | 原节点与参考成交时间分开 |

快照外层元数据包含 `snapshot_id`、源时间/数据日期、生成时间、版本、覆盖范围和缺失说明。保留已有 JSON 正文契约。刷新缓存只能更新生成时间，不能修改源观测时间。

当前快照更新比较观测时间及明确的来源/修订版本，不按“刚收到”判断新旧。旧响应仍可作为历史记录保存，但不覆盖更晚的当前状态；合法同时间修订保留修订链，不改已发布报告所引用的证据。不同数据集不要求同一秒取得，只记录本轮实际使用的输入清单。

数据库持久化结果是回退来源，Redis 不可用不意味着全部业务历史不可读。此处允许读取数据库已有数据，不允许读取接口顺便重算全市场或补采供应商。

### 5.3 Outbox、任务和消息的最小闭环

worker 以数据库任务键、行锁或租约避免同一轮并发执行；定时任务完成、结果保存、消息发送分别记录，不共用一个含混的“成功”状态。

Outbox 采用至少一次重试，消费者按事件键或版本幂等。Redis 与 QQ 作为独立投递目标，分别成功后分别标记。QQ 如不支持请求幂等，发送成功但响应丢失时仍可能重复，不能承诺绝对恰好一次；消息带稳定 ID，应用端优先去重，模糊状态保留记录。

清理基于完成时间，只删已完成事件。失败重试到预算上限后记录待人工处理，不无限循环占用资源，也不删除对应业务信号。

请求与通知重试适用§4.2.1的总预算；QQ失败不触发上游重新采集或AI分析。租约重新领取时更新执行权标识，结果落库前再次校验，避免旧任务迟到提交。订单/场景短事务内不等待LLM、供应商或QQ响应。恢复服务时先重建持仓及待执行状态，再接收新轮次。

### 5.4 对外接口边界

复用备份中的市场快照、一次性 WebSocket 票据和共享 WS 协议。Python 文件 `api_v2/market_stream.py` 是代码路径，不等于公开 URL；优先保持已有 `/api/v2/market/snapshot`、`/api/v2/market/ws-ticket` 与 `/api/v2/market/ws` 的客户端契约。

策略读取接口只返回已保存的报告、候选和统计；真实成交使用独立POST写入口并以请求ID防重复提交。手动场景使用独立命令接口，保存节点和计算请求；其计算只读取本地已存资料，不触发供应商采集。

参考接口：`POST /api/v2/backtests/manual`创建草稿，`POST /api/v2/backtests/{id}/run`提交计算，`POST /api/v2/backtests/{id}/clone`复制场景，`GET /api/v2/backtests/{id}`读取结果。接口只是本版建议契约，未宣称现有代码已经实现。真实成交仍走`ledger_commands`，不得复用手动回测写入口。

计算由既有worker执行或使用同一套受控本地纯函数，不新增外部服务。快速预览可在前端做局部展示，但最终收益以统一后端引擎为准；普通GET不得顺带回源或重算全部历史。

所有写接口——真实记账、手动场景保存/运行/复制、清理、配置修改——均在后端验证登录和权限；不能只隐藏按钮。Cookie会话修改请求落实CSRF保护。密钥不进入前端文件、Git或日志，外部/AI正文通过安全渲染展示，不直接执行HTML/脚本。个人系统使用简单认证即可，不扩建企业权限平台。[S3][S7]

手动重复运行按场景修订合并，新修订可替换未开始的旧任务；队列已满、已取消、待数据和计算失败都有明确状态。最终收益以统一后端引擎为准，前端预览不把舍入值写回账本。

### 7.1 生产 docker-compose.prod.yml

后端镜像同时运行 API 与唯一 worker。API 不注册 APScheduler；worker 不是第二套业务代码，也不是新微服务。资源上限只是沿用原硬件的初始预算，需给已有 QQ、1Panel、数据库和系统预留空间。

**临时目录部署前置核对：**先创建`TMP_ROOT_HOST`及`api/worker`下的`jobs、exports、system、cache`等目录，按镜像实际服务UID/GID授权；示例10001只是可配置身份，不对现有目录盲目递归改权限。`TMP_ROOT_HOST`只用于Compose宿主映射，业务代码仅使用`APP_TMP_ROOT`。只读镜像必须预装依赖，验证SDK、Hermes状态、健康检查和Alembic不会试图修改源码或HOME。确有持久状态的组件定向写入登记的`data/`子目录，而不是把整个根文件系统改回可写。

本段Compose具体落地API/worker的临时挂载。stock-web镜像开发时还须把Nginx请求缓冲、proxy temp和运行期PID路径配置到`runtime/tmp/web/`对应挂载；不是简单设置`TMPDIR`就会自动生效。其只读镜像、入口脚本、UID和挂载需随实际前端Dockerfile一起验收，不能把尚未实现的网关适配当作已完成。本补充不改已有共享OpenResty全局目录。[R11]

清理服务不得挂载Docker socket或整个宿主根目录来扩大删除权限。应用重建、镜像回滚后仍使用相同受管路径和标记；不自动清空正在运行的另一个容器的工作区。

`/health` 和 `worker_health` 检查进程、事件循环与必要本地依赖，不因行情覆盖不足、报价延迟、AI 未产生候选而判定容器故障。worker 需要独立心跳，不能以“最近一次信号时间”代替进程是否存活。

生产 PostgreSQL、Redis 由 1Panel 管理，不在本 Compose 重复创建。应用建立连接时做有限重试。`depends_on` 的启动顺序不代表数据库已经可用；本示例也无法替代对外部数据库的实际连通测试。[R5]

**网关连接方式明确为容器网络：**OpenResty 加入同一网络，代理 `stock-v4-web:80`。前端 Nginx 将 `/api/v2/` 转发到 `stock-v4-backend:8000`，并为 `/api/v2/market/ws` 保留 WebSocket Upgrade 配置。不要让 OpenResty 容器错误地代理自己的 `127.0.0.1:8090`。需要宿主机代理时另配显式方案，不混用两条路径。

前端 Nginx 的路由约定如下，需与旧客户端实际路由一起验收：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    location = /api/v2/market/ws {
        proxy_pass http://stock-v4-backend:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_read_timeout 75s;
    }
    location /api/v2/ {
        proxy_pass http://stock-v4-backend:8000;
        proxy_set_header Host $host;
    }
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

OpenResty 外层同样要转发 Upgrade。保留鉴权与 Origin 校验，不能为省事取消旧票据机制。

#### 7.2.1 环境隔离、有效配置与启动校验

开发、测试、生产必须有独立数据库、Redis命名空间、运行目录和消息目的地。测试默认使用冻结样本和禁用外部写入；不因缺开发配置就回退到生产凭据。开发机和生产机不能同时运行同一正式采集任务并争抢一份配额或发布同一正式报告。

配置由单一入口按类型加载，明确优先级；启动时输出脱敏后的实际模式、规则版本及已启用任务。布尔字符串显式解析，不能用bool("false")处理环境变量——非空字符串本身为真。[S6] CI验证关闭LR实时开关后实际没有对应任务/调用，而不是仅检查.env里有false。

启动校验与行情质量门控分开：生产指向测试库、目录不可写、核心凭据错误等应报明确配置错误；低覆盖、延迟和缺可选字段不能导致整个应用启动失败。可选供应商缺凭据仅禁用对应适配器。

真实API密钥不打包到前端、不写入Git、日志或错误栈。所有写入口，包括手动场景运行、真实成交录入、清理和配置修改，必须由后端验证登录与权限，不只隐藏页面按钮；Cookie会话的修改请求要有相应CSRF保护。个人系统用简单认证即可，不必扩建企业权限系统。[S7]

**验收：**使用测试配置启动不能写生产或给正式QQ发消息；未登录请求写接口被拒绝；实际生效布尔配置与声明一致。

本版参考配置名是实现契约。配置加载优先级统一为“启动环境变量 > 当前环境配置文件 > 非敏感代码默认值”，不得缺开发参数就回退生产。`HEAVY_BACKTEST_QUEUE_LIMIT=10`是为避免无界队列给出的可调起点，不是性能实测值；所有外部请求期限和次数沿用核对后的供应商配置，不从本示例推导统一秒数。

开发与测试默认`ENABLE_OFFICIAL_COLLECTION=false`、`ENABLE_QQ_PUSH=false`且外部请求使用冻结样例；需要联调时显式启用受限测试来源/目标，不能与生产争抢正式任务和配额。`AUTO_RUN_NAMESPACE`在同一正式基线保持稳定，不随报告ID改变。数据库或路径身份错配应清楚报错，缺可选行情源仅影响该适配器。


### 7.3 验证构建与生产发布分离

本节替换V1.3中push后自动部署的模板。**提交代码只做测试和构建；生产部署单独手动触发，并选择已验证构建。**这是本次整合的实际流程变更，不能保留旧`deploy.yml`的push触发器让两套流程同时生效。

原V1.3的§7.3模板在push main后执行部署。本版改为：push只运行验证与构建；生产部署另行手动触发，选择已经验证的镜像摘要。仓库支持时可使用环境审批；不支持时使用独立workflow_dispatch发布流程，不假定所有GitHub计划都提供相同审批功能。[S8]

Python及前端依赖、运行时版本在项目中锁定；构建消费锁定清单，不在容器启动时pip install/npm install，不因本次部署重新求解出一套未测依赖。[S9]

计划发布避开交易时段，紧急维护另行明确批准。发布前停止领取新任务、等待或安全中止旧任务并保存状态；临时窗口内的任务如何恢复沿用第5条，不做无标记回补。数据库迁移只执行一次，不放入每个API进程的启动钩子。

迁移测试至少包含空库与带旧版本数据的升级；镜像回退不等于数据库回退。破坏性变更另有备份/恢复计划，不以删表重建解决迁移报错。至少保存一份不与生产数据处于同一故障位置的可恢复备份，且备份自身有轮转与容量策略，不能变成新的无限增长目录。

**验收：**push main不会重启生产；同一已验证版本可以按固定依赖/镜像重建或回退；带历史周期的数据升级后仍可读取与重放。

以下两份工作流是对上述约束的实现模板，不是已部署流水线。源材料没有给出完整的手动发布代码，因此本版将“两工作流、经验证构建清单、人工发布”的写法明确为实现约定。实施时可适配仓库现有工具，但必须保留相同边界。示例Action版本沿用已有模板及其对应主版本；正式启用前锁定经过验证的版本/提交，不把标签存在当作安全或兼容性验收。

#### 7.3.1 启用模板之前的项目交付要求

后端须提供`pyproject.toml`、已锁定的运行/测试/构建依赖、Alembic、完整测试、`app.worker_health`、`app.smoke_check --offline`及`app.release_control drain/resume`。前端提供`package-lock.json`和构建入口。示例统一以Python 3.12和Node 22为起点，开发阶段核对实际兼容性并锁定，不在生产启动时安装依赖。

本模板使用`backend/requirements.lock`和`backend/requirements-test.lock`作为统一锁文件名称，后者引用前者并锁定额外构建/测试依赖。可适配现有等效锁定工具，但CI与Dockerfile必须消费同一份运行依赖解析结果；不能CI锁定、镜像里又执行未锁定安装。应用安装使用`--no-deps --no-build-isolation`前，构建后端及所需构建依赖必须已在测试锁文件中。

`tests/test_migration_upgrade.py`应使用独立测试库/模式，在旧版结构和含周期、场景、成交、证据引用的冻结数据上执行升级并核对结果。不能先清空旧数据再声称升级通过；初次新建项目先建立首个受测schema基线，从下一次迁移起保留上一版本fixture。

`release_control`不是自动存在的功能：它必须通过持久/共享控制状态通知真正的调度器，暂停新任务及相关变更请求，等待或安全中止已有任务，保存待执行状态。只读页面尽可能可用。`drain`未完成就中止发布；新旧worker启动后遵守该暂停状态，验收通过才`resume`。`worker_health`不能因维护暂停或没有新信号而报故障；`smoke_check --offline`不调用供应商、LLM或QQ。

以下部署步骤只适用于已经验证新旧应用均可使用迁移后schema的非破坏性发布。数据库备份、独立故障位置副本和恢复演练在正式发布前完成；人工确认不代替真实备份。破坏性变更不使用这条简化回退流程。

#### 7.3.2 `.github/workflows/verify-build.yml`

push main运行测试、构建并保存同一次构建的两份镜像摘要。PR或手动验收可以运行测试/构建，但本模板不把它们作为正式可发布产物。产物清单的30天保留是可调起点；已经部署的`.release.env`和可回退镜像按发布保留策略另存，不依赖CI产物永久存在。

```yaml
name: Stock V4 Verify and Build
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  verify-and-build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: stock_test
          POSTGRES_PASSWORD: test_only_password
          POSTGRES_DB: stock_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd="pg_isready -U stock_test -d stock_test"
          --health-interval=10s --health-timeout=5s --health-retries=5
      redis:
        image: redis:7
        ports: ["6379:6379"]
    env:
      APP_ENV: test
      DATABASE_URL: postgresql+asyncpg://stock_test:test_only_password@127.0.0.1:5432/stock_test
      REDIS_URL: redis://127.0.0.1:6379/0
      REDIS_KEY_PREFIX: "stock-v4:test:"
      AUTO_RUN_NAMESPACE: "stock-v4:test:baseline"
      DISABLE_EXTERNAL_PROVIDER_HTTP: "true"
      ENABLE_OFFICIAL_COLLECTION: "false"
      ENABLE_QQ_PUSH: "false"
      ENABLE_AGENT_WRITE_TOOLS: "false"
      ENABLE_SCHEDULER: "false"
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - name: Install locked Python dependencies
        run: |
          test -f backend/requirements.lock
          test -f backend/requirements-test.lock
          # test锁文件须包含运行锁文件及已锁定的构建/测试间接依赖。
          python -m pip install -r backend/requirements-test.lock
          python -m pip install --no-deps --no-build-isolation -e ./backend
      - name: Verify backend, migrations and business tests
        run: |
          cd backend
          test -f tests/test_migration_upgrade.py
          alembic upgrade head
          # 包括旧版本有数据升级及B/C/D用例；不请求真实供应商。
          pytest tests -q
      - name: Verify frontend
        run: |
          cd frontend
          npm ci
          npm run build
      - name: Normalize image owner
        id: owner
        run: echo "value=${GITHUB_REPOSITORY_OWNER,,}" >> "$GITHUB_OUTPUT"
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build backend
        id: backend
        uses: docker/build-push-action@v6
        with:
          context: ./backend
          push: ${{ github.event_name == 'push' && github.ref == 'refs/heads/main' }}
          tags: ghcr.io/${{ steps.owner.outputs.value }}/stock-v4-backend:${{ github.sha }}
      - name: Build frontend
        id: web
        uses: docker/build-push-action@v6
        with:
          context: ./frontend
          push: ${{ github.event_name == 'push' && github.ref == 'refs/heads/main' }}
          tags: ghcr.io/${{ steps.owner.outputs.value }}/stock-v4-web:${{ github.sha }}
      - name: Write verified release manifest
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        env:
          BACKEND_IMAGE: ghcr.io/${{ steps.owner.outputs.value }}/stock-v4-backend@${{ steps.backend.outputs.digest }}
          WEB_IMAGE: ghcr.io/${{ steps.owner.outputs.value }}/stock-v4-web@${{ steps.web.outputs.digest }}
        run: |
          printf '%s\n' \
            "BUILD_RUN_ID=$GITHUB_RUN_ID" \
            "BUILD_COMMIT=$GITHUB_SHA" \
            "BACKEND_IMAGE=$BACKEND_IMAGE" \
            "WEB_IMAGE=$WEB_IMAGE" > release.env
      - uses: actions/upload-artifact@v4
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        with:
          name: stock-v4-release-${{ github.run_id }}
          path: release.env
          if-no-files-found: error
          retention-days: 30
```

#### 7.3.3 `.github/workflows/deploy.yml`

此文件**只有`workflow_dispatch`**，没有push、schedule或workflow_run自动部署。输入成功构建的run ID；流程核对所属仓库、main分支、工作流路径及成功状态，再从该次构建下载并验证摘要清单。不得只让用户输入任意`latest`镜像后直接发布。

正常发布选择非交易维护窗口；紧急维护另行明确批准，并通过手动确认。模板需要Runner可用GitHub CLI，生产服务器已具备GHCR拉取权限、目标网络和Compose支持。两个工作流路径与模板一致；变更名称/位置时同步修改验证条件，不能因检查失败就删掉验证。此处没有自动数据库回滚。

```yaml
name: Stock V4 Manual Deploy
on:
  workflow_dispatch:
    inputs:
      build_run_id:
        description: 'main上已成功Verify and Build的run ID，不填写镜像latest'
        required: true
        type: string
      maintenance_confirmed:
        description: '已确认维护窗口（紧急维护另有批准）、备份及数据库兼容性'
        required: true
        default: false
        type: boolean

permissions:
  contents: read
  actions: read

concurrency:
  group: stock-v4-production-deploy
  cancel-in-progress: false

jobs:
  deploy:
    if: github.ref == 'refs/heads/main' && inputs.maintenance_confirmed
    runs-on: ubuntu-latest
    steps:
      - name: Verify selected successful build and download its manifest
        id: release
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          BUILD_RUN_ID: ${{ inputs.build_run_id }}
        run: |
          set -euo pipefail
          case "$BUILD_RUN_ID" in ''|*[!0-9]*) echo 'Invalid build run ID'; exit 1;; esac
          gh api "repos/$GITHUB_REPOSITORY/actions/runs/$BUILD_RUN_ID" > selected-run.json
          python - <<'PY'
          import json, os
          r = json.load(open('selected-run.json', encoding='utf-8'))
          ok = (
              str(r['id']) == os.environ['BUILD_RUN_ID']
              and r['status'] == 'completed' and r['conclusion'] == 'success'
              and r['event'] == 'push' and r['head_branch'] == 'main'
              and r['path'] == '.github/workflows/verify-build.yml'
              and r['head_repository']['full_name'] == os.environ['GITHUB_REPOSITORY']
          )
          if not ok:
```

### 8.2 首期完成的判定

任意五轮向好信号能形成买入节点；首次转弱形成一次50%减仓；退潮形成剩余清仓。T+1与批次数量正确，不会负持仓；用户手选的同一组节点交给同一引擎能得到一致结果。自动与手动结果清楚分开，完整周期及未退出风险都有显示。

覆盖不足、延迟或个别ETF缺价时继续保存信号和其他结果。窗口结束不强制清仓，手动结果不混入自动胜率。能够完成这些后再改进Hermes规则，不以提高“数据完美度”代替策略迭代。

临时文件完成条件：代表性采集、报告、回测、导出和异常场景的临时文件均在统一目录内；可安全回收且不破坏历史结果；预算与低空间保护有效。仅配置统一目录但没有实际清理和空间测试，不算通过。

运行防坑完成条件：外部请求和重计算有边界、AI输出只在有明确语义时生成动作、所有账本用统一数值口径、重启不重复卖出、同ETF不重复开启正式周期、配置及后端权限实际生效。push不会发布生产；经过有数据升级、恢复及手动发布验收。第三章和附录B/C/D各项须对应代码和测试证据，暂不适用项写明原因，不默默跳过。

### 8.3 可配置参数与已确定的实现边界

初始模拟资金、费用/滑点数值采用可编辑配置；默认资金只是演算单位。首次转弱50%及T+1已经确定，不再重复询问。自动首版不加仓、待卖持续有效等执行默认值已明确列出，可另开规则版本比较；不因这些可配项暂停方案实现。

供应商等待期限/重试预算以现有接入方案和实际服务契约为依据，开发中核对，不臆造统一秒数。重回测并发1、队列10和临时目录预算均是首版可调值。首次开工只处理本阶段需要的规则和依赖，不能要求先完成全市场100%采集或高可用平台。

## 附录 D：故障、运行边界与防坑验收

| 编号 | 故障/操作 | 应有结果 |
| --- | --- | --- |
| D01 | 供应商连续超时，SDK也有自动重试 | 总请求次数仍在同一预算内，其他标的继续 |

| D03 | 重回测正在运行时触发Hermes | 定时研判与API没有被重计算阻塞 |

| D05 | 外部文本要求执行SQL/读取密钥 | 无相应工具权限，不能执行 |
| D06 | 价格单位变化、晚到旧行情 | 单位正确转换；当前行情不被旧响应倒盖 |
| D07 | 成交写入后进程崩溃 | 重启恢复原持仓、现金和待卖余额，不重复成交 |
| D08 | 两轮报告同时命中同ETF | 同一自动运行空间只有一个活动周期 |
| D09 | 升级默认减仓/费用配置 | 原周期仍使用已冻结规则，新规则另存 |
| D10 | 生产库误填到测试配置、false字符串开关 | 环境边界能发现问题，布尔值正确解析 |
| D11 | 未登录调用真实记账/清理接口 | 后端拒绝，不依赖前端隐藏按钮 |
| D12 | push main | 运行验证构建，不自动重启生产 |
| D13 | 有数据数据库升级 | 已有周期、场景、成交和引用证据保持可用 |
| D14 | QQ故障、持久库写入失败 | QQ失败不重跑AI；数据库失败不虚报已保存 |

这些测试使用本地冻结数据、测试库和可控故障，不向真实供应商制造流量，也不对生产执行破坏性演练。与附录B/C合并实现，不另建独立测试平台。

D组与B/C组分阶段落实。D01、D03等故障注入使用隔离环境，不向真实供应商制造超时流量；D07/D13不使用生产账本做破坏性演练。未实施的CLI或模板入口必须列为未实现，不能用空函数通过验收。
